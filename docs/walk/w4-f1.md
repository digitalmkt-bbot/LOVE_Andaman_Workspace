# w4-f1 · Dashboard, Action Board, booking calendar and the range reports (2026-10-18)

Branch `wire/w4-f1`. Server side: operation-backend `todo/b1-sales-dashboard-model.md` and `todo/b2-reports-model.md`
(endpoints in its README: "Sales dashboard, day detail and Action Board" and "Range reports").
Idiom: every legacy function is wrapped from `js/ops/73-ops-*.js`; legacy answers outside operation mode, until the first
server answer arrives and when a read fails. The screens keep legacy's markup, dialogs and texts; the figures are the server's.
One marked edit in a legacy file (see "Edits outside ops/").

New files (script tags added in `allotment_v2.html`, after `65-ops-meals.js`):
`73-ops-srv-reads.js` (shared cache) · `73-ops-dash-detail.js` · `73-ops-dash-series.js` · `73-ops-action-board.js` ·
`73-ops-bk-calendar.js` · `73-ops-cancel-report.js` · `73-ops-b2b-dash.js` · `73-ops-rep-ops.js` · `73-ops-our-mix.js` ·
`73-ops-pickup-map.js` · `73-ops-prep.js` · `73-ops-analysis-why.js`.

`laOps.srv.read(key, path, params, onLand)` (73-ops-srv-reads.js) answers from the cache, starts the read when there is none or when
a write made it stale (the old answer stays on screen until the new one lands), redraws once when it lands, and shows a failed
read once. Nothing there computes a figure.

## 3. Decisions I took (each reversible)

1. **Dashboard bars keep the screen's own windows** (last 30 days, last 12 months), put together from two server answers (this month and the one before; this year and the one before). The server's `series_stats` and `top_routes` describe a calendar month, so the top three routes, "Other", best and slowest bar and the average are still added up by `renderDash` over the server's bars. One marked edit in `04-data-core.js`.
2. **Reads are cached per screen range (`laOps.srv`)**; a write makes them stale; the old figures stay until the new ones land. No answer yet: loading placeholder where the old render would be empty (Action Board, PR/PO), legacy's arithmetic elsewhere. A failed read: legacy's own way, with its loads.
3. **Booking loads removed where the server answers**: Action Board (3 ranges), Operations Report (2 periods), Pickup Map (2 periods), PR/PO (the range), Cancellations (the month). The adapters that started them (52, 56, 41) are untouched; their `bookingV2EnsureOpsRange` is switched off for the length of the call.
4. **Cancellations**: the window is the picked month sent as `from`/`to`; the server windows by the day the cancellation was made, so the line above says "Cancelled in:" where legacy said "Travel period:". The City Tour page keeps legacy's report (no kind filter on the server).
5. **B2B**: a route group of the screen (Phi Phi, Similan, Surin, Krabi, Other, decision Q13) that is exactly one server family uses the server; Phi Phi (two families) and Other (six) keep the browser's sums over the trip lines. The trip lines (55) stay for the detail pages, the stacked monthly charts and the default reference day.
6. **Calendar matrix and cards are copies of legacy's markup** fed from the answer (not a rewrite of the screens).
7. **Operations Report**: the finance slide reads `SB_INVOICES`, so for the call it gets rows that carry the server's totals (restored right after); no edit in 08-app.js.
8. **Analysis matrix**: 44 owns the page; this file appends the matrix from the same answer (it watches `laOps.get` for the analysis path, so there is no second 30-second read).

## 4. Differs from legacy (developer to confirm; mostly the server's decisions in the two model notes)

- Day detail: the keyed-time bars use Bangkok hours (legacy used the browser's). Later months in "Today's bookings · travel date" have no day rows under the month (the server serves the next 7 days one by one and later months as a total).
- Dashboard month bars: 31-day calendar-month answers are cut to the screen's last 30 days; the year bars stop at today (server) where legacy stopped at the picked day.
- Calendar: a family's "bookings" count excludes cancelled bookings; zone (PK/KL/NT) is the trip's own.
- Cancellations: window by cancellation date (decision 4 above); counts all bookings (marine page).
- B2B: route family names are the catalogue's (grouped to five by the Q13 table).
- Operations Report: a voided invoice is neither raised nor unpaid; seats offered ignore whole-boat holds.
- Our mix: nationality is not guessed from a name; the mix of a booking is its passengers'.
- Pickup Map: a booking worth counts in every period one of its trips falls in (server decision 8, left as legacy).
- PR/PO: a trip split over boats has one row per boat.
