## Decisions taken (design mindset: the server computes, the screen shows; reverse any of them)

1. **Dashboard:** `ops/73-ops-dash-series.js` is left in place but its `laOpsDashSeries` is replaced by 91's. The old stitched version (two calendar answers) is no longer asked.
2. **Calendar route-set dialog closes only on success** (legacy closed first). A refused save keeps the dialog and the typed name, which is what legacy's own empty-name refusal already did.
3. **Closing a day: the impact modal now opens after the server's 409**, not before the request. A closed day in the past is not listed (the server's rule: only days from today strand anything). Charter boats in the list are marked from the browser's `TRIPS` (`charterBookingId`) because the server's `boats[]` does not say; if the browser does not hold the day, a charter boat is listed with the other boats.
4. **Calendar month grid keeps its per-boat chips** (see row 3).
5. **`flExtraToCol` keeps legacy's confirm with its `cur + add = total` line** (a hint for the person, the browser cannot ask the server for a preview: the endpoint has no dry run). The stored figure is the server's, and a difference is told.
6. **Duplicate check before the save:** when the server answers, its list replaces legacy's scan entirely (the server's answer is the one that counts). A form the check refuses falls back to legacy's scan; the save then gives the real refusal.
7. **Pending-FOC flag on a row beats the browser's test; the pill's set still reaches unloaded months.** The flag alone could not replace the set (the all-time card counts months this browser has not loaded).
8. **Park month:** the day's per-type "should be issued" (`pc`) and a day's per-type tickets are added in the browser from the SAME answer's boats, because the month read gives day totals only for nationality and tickets as a whole.
9. **B2B detail pages keep legacy's drawing and are fed by `b2dSum`** (an entity filter is recognised by probing it with a line of that entity). A route group's class in the agent page is `b2dCls` on the summed server revenue of its families (same rule as the server's, applied to the server's two sums).

## Still missing (what a backend agent could add; the screen shows the browser's figure for these meanwhile)

1. **B2B entity pages, stacked monthly chart:** `monthly[]` carries revenue / pax / bookings per month, but the chart stacks by route (agent page) or by agent (sales and market pages). Needed: `monthly[].by_family { family: revenue }` for an agent, `monthly[].by_agent { agent_id: revenue }` for staff and market.
2. **B2B agent page, routes table:** `by_family[]` has revenue and class but not `bookings` and `pax` per family (two columns of the table), and there is no "routes sent" count or "latest 40 booking lines" (`recent[]`: booking date, travel date, family, pax, revenue). Those stay over the trip lines.
3. **Park month, per-type day totals:** `days[].by_type` (tickets per type) and `days[].pc` / `total.pc` (should-be-issued per type), so the overview needs no addition at all.
4. **Calendar month grid chips:** `GET /v1/availability/summary` `routes[].days[].boats[] {boat_id, trips, free_seats, sold_percent, tier, down}` would let the per-boat chips be the server's.
5. Optional: `POST …/extras/{id}/to-issue?dry_run=true` answering `{before, added, after, unit_mismatch}` without writing, so the confirm text itself can be the server's.
