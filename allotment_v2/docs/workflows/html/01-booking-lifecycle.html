Booking Lifecycle

Everything that creates, prices, guards, mutates and retires a booking record (SB_BOOKINGS) in Booking v2 — form, tabs, approvals, seat locks, and the cancel / reschedule / partial / weather flows.

01 What this does & who uses it

Booking v2 is the sales/ops hub of the app. One booking = one customer group, sold by one agent (or a B2C channel), travelling on one or more trips (routeId × date), each trip carrying its own pax mix and its own seat/charter mode.

RoleWhat they do here
Sales / reservation staffNew booking, edit, quote, FOC reason, discounts, voucher ref
Ops / dispatchBy-trip-date manifest, boat/van assign, re-confirm, pickup times
ManagerApprovals tab (pending_approval), FOC approve/reject
AccountingReads priceBreakdown / total / feeItems, raises invoices

The single-file client keeps SB_BOOKINGS in RAM :41531, loaded from the state blob at boot :41533. The durable store is Postgres. Two schemas coexist:

Uses trips[], per-trip pax and mode. Everything in this doc.

3.2 Edit an existing booking

Trigger — Edit on the detail page :78092.

1 · bkV2EditBooking(id) :77819
Refuses schemaVer !== 2; confirm()s if status is cancelled/completed/rejected; checks the advisory edit lock bkV2EditLockActive(bk) :77768 (5-min TTL, BK_EDITLOCK_TTL :77765).
2 · Deep-clone into _bkV2.newBooking
Deletes editLock, and re-hydrates arrays the relational backend drops when empty (addOns, passengers, adjustments, feeItems, altPickups → [], :77833) — without this the form crashes with “reading 'forEach'”.
3 · B2C special-case
priceMode='manual', manualTotal = existing total, and a _b2cSnap of the B2C-owned fields :77837.
4 · Set _bkV2.editingId, clear detailId, stamp the edit lock, render
5 · Save runs the same bkV2CommitBooking
editing looked up at :76702; id and createdAt preserved, updatedAt/updatedBy added.
The edit-preserve block is load-bearing :76855–:76919 newBk is built from scratch, so anything not explicitly carried over is destroyed: history, weatherResolve, rebook, invoiceId, paymentStatus, ops (boat/van assignment!), b2cOverride, upgrades, feeItems, reschedule, partialCancels, cancellation, cancelCategory, plus a resolved approval :76839 and a decided focApproval :76936. Losing ops silently wiped every boat/van assignment (fixed 2026-06-14).

Two deliberate un-preserves

Travel date changed :76883–:76896

Boat + van + van group + pickupTimeFinal + per-trip ops are wiped (charter keeps its boat), with a history line “วันเดินทางเปลี่ยน … ล้างการจัดเรือ/รถของวันเดิม”.

Pickup became self-arrive / NoTransfer :76900–:76911

If no alt-pickup still needs a van, clears the outbound van only (vanId, vanGroup, vanSeq, splits). vanReturnId is kept.

Also: an already-approved FOC does not downgrade to pending_foc on re-submit — it snaps back to confirmed :76939.

Seat-lock accounting on edit :76952–:76981 — bkV2ReturnBookingDraws(editing,'edit') returns everything the old version held, then the new draws are taken. Before this existed, editing a booking ten times counted the lock as used ten times (§lkReturn).

Failure modes — the edit lock is advisory only (last write wins). _bkV2DoCloseNewBooking :75078 clears it on discard; a crashed tab leaves a stale lock that expires after 5 minutes.

Restore (un-cancel) — bkV2RestoreBooking(id) :76386

Trigger: ↩ กู้คืน (Restore) on the detail page :78096 or the Tab-2 ghost row :72807.

  1. Refuses unless status ∈ cancelled|cancelled_weather|rejected; confirm()s.
  2. Voids any feeType==='cancellation' invoice.

3.5 Partial cancel (“Reduce pax”)

Trigger — − Reduce pax on the detail page :78094 → bkV2DetailPartial :77638 → bkV2PartialModal :77658.

  1. Modal lists every pax key in BKV2_PAX_KEYS :77632 (12 keys: ad/ad_fr/ad_th, chd*, inf*, foc*) with a “remove N” input, plus a charged vs waived split (bkV2PartialRecalc :77646 suggests ฿ amounts).
  2. bkV2PartialConfirm(id, tripIdx) :77702 — category required, note required for other, at least 1 pax removed; clamps each removal to the current t.pax[k].
  3. bkV2PartialCancel(id, tripIdx, opts) :77728 decrements bk.trips[tripIdx].pax[k] (seats free automatically because getSeatsConsumed reads live pax), reduces bk.priceBreakdown.total and bk.total by the refund, and appends to bk.partialCancels[].

3.6 Reschedule (move a trip date)

Trigger — Reschedule on the detail page :78093 → bkV2DetailReschedule :77624 → bkV2RescheduleModal :77486.

  2. bkV2RescheduleConfirm :77526 validates (new date required, must differ, reason required, partial amount > 0).
  3. bkV2RescheduleBooking(id, opts) :77545:
    • moves every trip.date === from to to; carries the charter TRIPS hold with it :77561
    • clears the day’s assignment — ops.boatId (unless charter), vanId, vanReturnId, vanGroup, vanSeq, vanSplits, pickupTimeFinal, and deletes ops.vanCheckin / ops.pierCheckin; same for every per-trip t.ops :77572–:77589

3.8 FOC approval · 3.9 The approval queue

FOC

Trigger — any trip with pax.foc > 0. bkV2SubmitBooking :76316 requires a focReason and commits with status='pending_foc'.

  • focApproval = {count, reason, status, requestedAt, requestedBy} :76795. Status is 'approved' immediately when the save status is confirmed, else 'pending'.
  • Approve bkV2FocApprove(id) :77360 — reason is mandatory (prompts if missing) → status='approved', bk.status='confirmed'. Reject bkV2FocReject(id) :77387 → bk.status='rejected'.
  • Boot-time reconcile :41622 fixes bookings whose FOC was approved but whose status got stuck in pending_foc/pending/quote.
  • Pricing: focDiscount is the forgone revenue — adult-fr rate × foc_fr + adult-thai rate × foc_th :77246 — stored as a negative number in priceBreakdown.focDiscount. FOC pax still occupy real seats in every allotment calc.

Approval queue (over-capacity / discount / B2C hold)

Tab รออนุมัติ :70758 → bkV2RenderApprovals() :70829. The list filters purely on status === 'pending_approval'.

  • bk.approval = {status, reason, targetStatus, over[], totOver, discount, saleName, requestedBy, requestedAt, approvedBy, approvedAt, note} :76832.
  • Reasons: over_capacity, discount, over_capacity+discount, and (server-side B2C holds) none at all — bkV2PendReason(b) :70874 infers closed_day / b2c_hold / over_cap, and bkV2EnsureApproval(b) :70886 creates the missing approval object on button click. Before this fix (§pendNoApproval 2026-07-31) the buttons silently did nothing for B2C-held rows.
  • bkV2ApprovalImpact(b) :70897 recomputes what the seats look like after approval (calls getAllotment(…, b.id) to exclude the booking’s own seats); …ImpactText :70914 renders it into the prompt. Over-license rows trigger a second confirm() :70930.
  • Approve bkV2ApproveBooking(id) :70922 — prompts for the approver’s name (required), sets approval.status='approved', bk.status = approval.targetStatus || 'confirmed', stamps confirmedBy/confirmedAt. Reject :70942 → rejected.
Seat-holding rule — bkPendHoldsSeat(bk) :12040 A pending_approval booking holds seats unless it was held for over-capacity (approval.over.length > 0 || approval.totOver > 0). Seats that don’t physically exist must not make seatsAvailable go negative. Discount / B2C / closed-day holds do reserve their seats.

3.11 Charter bookings · 3.12 OVN legs

Charter

  • trip.bookingMode = 'charter' (bkV2SetTripBookingMode :74725). Charter trips consume a whole boat, never seats: getSeatsConsumed skips them :12058, and baDayBoats / baCharterBoatIds remove chartered boats from the seat pool :45336, :45445.
  • Picking a boat that already has seat bookings opens a displacement confirmation: bkV2SetTripCharterBoat :74733 builds _bkV2CharterConfirm from getBookingsForRouteDate :12189, rendered by bkV2RenderCharterConfirmModal :70144; bkV2ConfirmCharter :74768 sets charterDisplacementAck = true.
  • Pricing :77128: starterPrice + max(0, pax − starterIncludes) × extraPerPax + paid longtail bundle, keyed by rt.charterRates[routeId][boat.type.toLowerCase()]. charterPriceMode:'manual' overrides and records manualDelta.
  • At commit :76989 (only when status !== 'quote') the boat is locked in Boat Operation: TRIPS[date][boatId] = {route, type:'charter', charterBookingId: bk.id}. Editing releases the old holds first :76708. bkV2CharterBoatHeal(date) :45435 mirrors trip.charterBoatId → ops.boatId so the charter booking appears on its own boat in the manifest.

OVN (overnight)

  • trip.ovn = null | 'return' (we bring them back) | 'self' (one-way). bkV2SetTripOvn :73919.
  • bkV2CreateOvnReturnLeg(idx) :73927 appends a second trip with the same route + pax, date = ovnReturnDate, ovnLeg:true, ovnOf: idx. It reserves seats on the return day but prices at ฿0 — bkV2TripSubtotal returns 0 immediately for ovnLeg :77125; the money sits on the outbound ovnCharge, added to totalExtra in bkV2CalcQuote :77271.
  • The return leg keeps a real zone (it needs a drop-off van) but must have no pickup time. bkV2HealOvnLegs() :45360, run at the top of bkV2RenderTab2, clears an inherited pickupTime and restores a zone an older build wrongly set to NoTransfer.

05 Persistence path

mutate SB_BOOKINGS (RAM array)
   │
   ├─ acctPersistBookings()  :42877   ← preferred; clears the charter memo (baChMemoClear)
   │                                    then laBlob().sb_bookings = SB_BOOKINGS; laBlobSave()
   ├─ bkV2PersistBookings()  :77383   ← delegates to acctPersistBookings when present,
   │                                    else manual read-modify-write
   └─ inline JSON.parse(localStorage[LS_KEY]) … obj.sb_bookings = … … setItem
                                        (bkV2CommitBooking :77005, bkV2CancelBooking :76373,
                                         bkV2RescheduleBooking :77613, bkV2PartialCancel :77757)
   │
   ▼
localStorage.setItem(LS_KEY, …)   ← SHIMMED at :80 (Storage.prototype.setItem)
   │  the blob never reaches disk; it lands in the in-RAM `_mem` variable
   ▼
debounce 1s → save(v)             ← only when `_syncReady` (real /api/load succeeded) AND laCanEdit()
   │
   ▼
computeDiff(BASE, cur) → laDiffToOps() :167 → POST /api/v1/_batch   (put / per-field patch / del)
   fallback: any key the REST index doesn't know → legacy whole-diff POST /api/save

Notes that matter for this domain

  • All four write paths are read-modify-write on the whole blob — none clobber sibling keys, but each re-serializes the entire ~6 MB state. Prefer acctPersistBookings() in new code: it goes through the laBlob() cache :42860 and invalidates the charter memo.
  • acctPersistBookings and sbSeatLocksPersist are permission-gated by laCanEditArea('operations') — a view-only user’s mutations stay in RAM and never sync.
  • Seat-lock writes go through sbSeatLocksPersist() :41651 (blob key sb_seat_locks), independent of the booking write — so a commit that draws locks issues two blob writes; the 1 s debounce collapses them into one batch.
  • Load side: boot reads d.sb_bookings with Array.isArray :41533 and window._laReloadData() re-reads it on soft refresh. A key persisted but not listed there vanishes on refresh.
  • TRIPS is only written to the blob when a charter hold changed (tripsModified :76990, lockMoved :77618).

06 Cross-module contracts

Booking → Boat Operation

Charter: booking writes TRIPS[date][boatId] = {route, type:'charter', charterBookingId} at commit :76994, deletes it on cancel :76361 / edit :76708, and moves it on reschedule :77561. Booking reads TRIPS for capacity through getAssignedBoatsForRouteDate :12096 → getAllotment :12145.

Booking → boat/van assignment (another domain’s code)

Booking owns the ops container, not the assignment UI. Access it only via bkOpsRead(b,date) :45392 / bkOpsFor(b,date) :45399 / bkOpsClear(b,date,opts) :45407. Day 1 lives on bk.ops; day 2+ on trip.ops (bkIsFirstDay :45387).

Assignment fns belong to fleet/dispatch: bkV2AssignBoat :45500 (guard cap + BA_CAP_TOL(2)), bkV2AssignVan, bkV2AssignVanReturn, bkV2SetReturnSameVan, bkV2VanGroupSetVan, bkV2VanSplit, bkV2BoatSplit.

What booking writes into ops itself: only clearing — on a date change during edit :76886, on self-arrive/NoTransfer :76900, and on reschedule :77572 — plus bkV2SyncAltPickupSplits(newBk) :46258, which builds ops.vanSplits[] so each alt-pickup point can ride its own van. bkV2RetInfo(bk,date) :45695 is the contract for “is the return leg handled?”.

Booking ← Rate Types

bkV2GetRT() :77091 (base rate) and bkV2GetRTForTrip(t) :77112 (per-trip promo overlay via bkV2ResolveRateType, reading SB_CONTRACTS where kind==='promo') — a promo is adopted only if it actually prices that route. Reads rt.seatRates[routeId][zone]['adult-fr'|'child-fr'|'adult-thai'|'child-thai'], rt.routeBundles[routeId].longtail (gated by _rtBundleAppliesTo), rt.charterRates[routeId][boatType], rt.addOns.longtail (normalised by _rtNormalizeLongtail) and rt.addOns.privateTransfer[route][zone][vehicle].

Booking ← Agent

sbGetAgent(bk.agentId) gives payType → paymentSnapshot.method, creditDays → netDays, contractVersion, sales (discount approval routing :76691), programPeriods/programs (contract route whitelist :76570), bookingChannel.cancelPolicy (shown in the cancel modal :77439).

Booking → Accounting

acctBookingBase(bk) :42882 reads bk.total || bk.priceBreakdown.total; acctBookingTotal adds feeItems. Booking calls acctVoidInvoice, acctCreateFeeInvoice, acctCreateDeposit, acctBookingInvoice, acctInvoicePaid, sbInvoicesPersist. Credit exposure is derived from confirmed, credit-mode, unpaid bookings — booking stores no ledger.

Booking ← B2C sync (server)

Bookings whose id starts b2c_ are owned by the B2C source. BKV2_B2C_OWN :77781 maps app field → DB column; bkV2B2CSnap/bkV2B2CDiff record which of those fields ops changed into bk.b2cOverride[] so the next sync skips them. Trips, pax, add-ons and money are always re-copied from editing on save :76867 — never re-priced locally.

07 Invariants & gotchas

  1. The edit-preserve block is load-bearing. Anything not copied in the if(editing){…} block at :76855 is destroyed. Required: history, weatherResolve, rebook, invoiceId, paymentStatus, ops, b2cOverride, upgrades, feeItems, reschedule, partialCancels, cancellation, cancelCategory, resolved approval, decided focApproval.
  2. Cancelled statuses are excluded everywhere — ['cancelled','cancelled_weather','rejected'] in getSeatsConsumed :12052, bkV2Aggregate :69090, flBoatBookingsFor, baSeatBookingsForRoute, bkV2FindDuplicateBookings, bkV2LockClaims. Add a new aggregate ⇒ add the filter.
  3. A booking can never silently eat locked seats. lockViolation :76672 is a hard block with no override; true physical oversell (over cap, within license) is a soft confirm() saving as pending_approval; over license is another hard block.
  4. Locks: children contribute 0 to the pool. bkV2LockPoolHold :41783 returns 0 for parentId locks — otherwise a parent’s seats are double-counted against getAllotment.
  5. Month/bulk locks use rolling per-trip release, not one global expiry — releaseDaysBefore + releaseTime :41696. Don’t carry a stale expiry onto a range lock.
  6. trips[].lockDraws is the source of truth for lock usage, not the used counter. Edit returns then re-draws; cancel returns; restore re-draws and reports shortfalls.
  7. bkPendHoldsSeat :12040 — over-capacity pendings do not hold seats; every other pending reason does. Changing this changes availability across the whole app.
  8. Timezone — build dates with bkV2LocalYMD(dt) :71746, never toISOString().slice(0,10). Some commit-path code still uses the latter for createdAt/bookingDate :76704, :76844; in +07:00 those can land on the previous day before 07:00 local.
  9. esc / escapeHTML is not global. Every renderer declares its own :69260, :70830, :77436, :78045. A new top-level render fn that forgets it throws silently on click.
  10. Scroll-jump — replacing #bkv2-host’s innerHTML while focus is inside it scrolls to top. Text inputs are protected by _BKV2_NO_RENDER_KEYS and targeted DOM updates like bkV2VoucherLiveCheck. Follow that pattern for new inputs.
  11. Booking ids need the random suffix. bkV2GenerateBookingCode :75089 uses MAX (not count) for the sequence and appends 4 random chars; without it two concurrent tabs generate the same id and the record-level diff merge silently overwrites one booking with the other.
  12. Charter never consumes seats, and availability only drops if the boat is reserved in Boat-Op TRIPS (getSeatsConsumed, baDayBoats, getAssignedBoatsForRouteDate — which also consults baCharterBoatMapMemo so a split-charter second boat isn’t resold).
  13. The _bkV2 state comment is stale (says 3 tabs, there are 6) and so is docs/BOOKING.md. docs/booking.model.ts is accurate.
  14. CHANGELOG.md does not exist in this repo, so the in-code §tag comments are the only surviving history: §pendSeat :12037, §lkReturn :41849, §lkBulk, §b2cSave, §b2cEdit, §eat, §pickup guard, §altPickups, §OVN, §pendNoApproval, §bug1, §apprCap, §down, §rate, §hotelDedupe, §syncGate, §emptyBlobGuard.
