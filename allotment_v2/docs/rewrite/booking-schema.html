Why it exists 01

The point is not tidier storage. Three whole classes of live bug stop being expressible once the shape changes — they are deleted by construction, not fixed by vigilance.

pax{ ad_fr, ad_th, chd_fr, … }
booking_trip_pax rows

One row per pax type per trip replaces the twelve-key object, and kills the legacy ad vs ad_fr dual shape that every aggregate has to special-case.

bk.ops (day 1) + trip.ops (day 2+)
booking_ops per service_date

Every day gets a row. This is the split behind the edit-preserve bug, where rebuilding a booking silently wipes its boat and van assignment.

lock.used stored counter
derived view over draws

A counter that drifts needs repair tools. Deriving it deletes bkV2LockAudit, LockCoverage, LockFixUsed and LockFixTree outright — the spec says do not port them.

Anchor tables 03

Five of the nineteen carry design decisions worth stating explicitly. The rest are ordinary child tables.

TableDecision
bookingBusiness code survives as a natural key alongside a surrogate UUID PK. Two formats exist in live data: v2 generates BK-YYMMNNNN-XXXX from local time with a MAX-based sequence, legacy v1 generates BK-YYMMDD-NNN-XXXX from toISOString() with a count-based sequence. Both land in this column at BK-04, so no format constraint can assume one shape.
booking_trip(booking_id, trip_index) unique. Carries route, date, zone, booking mode, charter fields and OVN fields.
booking_trip_paxOne row per pax type per trip. Replaces the twelve-key pax{} object and the ad/ad_fr dual shape.
booking_price_breakdownSeat, addon, FOC discount, discount, extra, total — signed. Discounts stay negative exactly as today.
booking_ops(booking_id, service_date). Replaces the day-1 / day-2+ ops split entirely; every service day gets a row.

Constraints

  • Status as a Postgres enum or CHECK over the eight known values.
  • A trip in charter mode must have charter_boat_id IS NOT NULL.
  • All pax counts ≥ 0.
  • A partial unique index preventing two active bookings sharing a voucher_ref.
Cross-schema, by design

booking_attachment takes a real FK to the booking table even though the rows live in the allotment schema — 3,038 of them. Cross-schema foreign keys are legal in Postgres and are the right first step; physically moving the table can wait. Separately, booking_b2c_link replaces the b2c_<lkId> string-prefix convention with an enforced link to love_kingdom.bookings.

Seat locks 05

The subtlest correctness area in the app, and the source of an entire class of counter-drift bugs. LAM-94 · 5 pts

TableRole
seat_lockScope (day/bulk/month), route, date range, day-of-week, holder (agent/office/global), parent_id self-FK, qty, release rules, status.
seat_lock_usage(lock_id, trip_date) unique. Replaces the usedBy{date:n} object.
booking_trip_lock_draw(booking_trip_id, lock_id) with qty. The single source of truth.

Invariants to preserve

  • A child lock contributes 0 to the available pool — only parent and standalone locks hold seats. Enforced in the pool view, not with a table constraint.
  • Month and bulk locks use rolling per-trip release (release_days_before + release_time), never a single global expiry.
The acceptance test should be impossible to fail

For any sequence of draw, return and edit operations, the derived used equals SUM(booking_trip_lock_draw.qty) for live bookings — by construction. That is the tell that the model is right rather than merely tested.

Availability 06

getAllotment is consulted by every consumer and is the thing that must never be wrong. It becomes a view. LAM-96 · 5 pts

seats_available = available_capacity − seats_consumed − locked_seats
  • Exclude cancelled, cancelled_weather and rejected from every aggregate.
  • Exclude booking_mode = 'charter' trips from seat consumption entirely, and remove charter boats from the pool.
  • Subtract check-in losses — no-show and on-site cancel.
  • A pending_approval booking holds seats unless it was held for over-capacity. Discount, B2C and closed-day holds do reserve.
Hazard — the view already exists and has drifted both ways

A v_seat_availability view is live in production and disagrees with the repo migration in both directions. Build from pg_get_viewdef, then supersede it with a new named view. Do not edit the old one in place, and do not trust the .sql file in the repo.

Acceptance is parity, not plausibility: for every (route, date) in the characterization fixtures, the view must return byte-identical numbers to the monolith. Differences get explained in writing, never adjusted away.

Migration 07

Backfilling the new tables from live production data — idempotent, re-runnable, and rehearsed on a clone rather than on fixtures. LAM-100 · 8 pts

  • schemaVer = 2 bookings migrate fully.
  • Legacy v1 bookings (programId + travelDate + pax{adult,child,infant}) migrate into the same tables behind a legacy_v1 flag, and stay read-only as they are today.
  • The dual pax shape normalises into booking_trip_pax rows.
  • bk.ops and trip.ops collapse into booking_ops keyed by service date.
  • The 22 parentless b2c_ bookings and 118 orphaned attachments carry through with the disposition assigned to them — never dropped silently.

Rate types 08

Booking cannot price a trip without rate types, so a minimum read-only slice of the sales domain is pulled forward. LAM-87 · 5 pts

The per-route longtail shape normalises at migration time, so the old flat shape never reaches the new schema. This is explicitly not the whole sales domain — that is Phase 2.

Blocked on 09

Two prerequisites sit on the critical path and neither has a sprint. This is the scheduling hole worth fixing first.

P0-09 · Orphan triage — adding a foreign key to data that already violates it simply fails

Three orphan sets are already known, and there are almost certainly more behind the 126 unenforced reference columns. Every one of those columns needs a recorded disposition before the FK migrations can run.

Known orphan setCount
allotment.attachments with no booking row118
ops b2c_ bookings with no love_kingdom parent22
love_kingdom bookings never synced to ops1
Do not delete production rows to make a constraint pass

An orphan is evidence of a real process gap, and someone needs to see it before it disappears. Dispositions are backfill, relink, soft-delete, or accept and leave the column nullable with no FK.

P0-08 · Cross-schema ownership map decides what the eight public tables actually are and how the B2C link works, before anything is built on top of them. love_kingdom is better modelled than operation_schemas — 39 of 39 tables have primary keys, against 120 of 133 — so where the two disagree, prefer its shapes.
