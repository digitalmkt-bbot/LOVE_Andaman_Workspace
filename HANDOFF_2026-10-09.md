## 2 · B2C change log (§b2cChg): how it works

- **Server:** `server.js` `relSyncB2C` plus a new pure module `b2c-changelog.js`.
  1. Before the upsert it snapshots the bookings that already exist.
  2. Before COMMIT it snapshots them again and diffs the two.
  3. It appends one row per changed booking to `sb_bookings__history`:
     - `kind:'b2c'`, `tag:'B2C'`, `by:'B2C sync'`
     - text in the shape `Label: old → new · Label: old → new`
     - a new booking gets `kind:'b2c_new'`
     - a line or order removed in B2C is logged as `Status: … → Cancelled` (the two cancel UPDATEs now use a CTE with RETURNING)
  4. It runs inside SAVEPOINTs, so if logging fails the sync still commits.
- **Guards:**
  - A full run that would log more than `B2C_CHG_BULK` changed bookings (env var, default 40) is treated as a mapper or catalog re-map and nothing is written.
  - `/api/b2c/reset` does not log "new".
- **Client:** `08-app.js`, under the `§b2cChg` block next to `bkV2HistTagColor`.
  - `bkV2B2CPending(bk)` reads the history after the latest `b2c_seen` entry. It merges the chains (Pax 2→3→4) and drops values that changed back to where they started.
  - By trip date shows a strip under the row (orange = edited, red = B2C cancelled, blue = new and travelling within `B2C_CHG_NEW_DAYS` = 2).
  - **รับทราบ** appends `b2c_seen`.
  - The header button "B2C changes N to review" opens a side list of every upcoming date, with moved-date bookings first.
- **Check on prod:** look for `[b2c-chg]` lines in the Railway logs after B2C edits a booking.
- **Known edge:** history is saved as a whole array. A client holding an older copy of a booking can, in a short window, save it over a history row the sync has just written. This race already exists for any two users editing history.

- The owner commits in parallel all the time. Before writing, prove the device file equals `git show HEAD:<file>` (compare md5). Then edit in place on the device, or stage → edit → commit back.
- **`device_commit_files` gotcha:** reusing a staged path can write the *old* content. Always copy to a fresh, uniquely named file under `/mnt/user-data/outputs/`, and check the md5 on the device afterwards.

